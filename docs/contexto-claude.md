UparAula (Laravel 11 + React 18/TS educational management app, spec in `PROMPT_UPARAULA_1.md`) is being built in phases because the full spec (~30 tables, 18 modules) is too large for one pass.

**Phase 1 — "esqueleto completo" — completed 2026-07-08.**

That deprecation notice, if displayed, gets echoed as HTML *before* headers are sent, silently breaking CORS/JSON headers. - The user's global npm cache (`~/.npm`) has root-owned files from a prior `sudo npm install`, breaking plain `npm install`/`npx`. Workaround used: pass `--cache <scratch-dir>` or `npm_config_cache=<scratch-dir>`. The user should eventually run `sudo chown -R $(whoami) ~/.npm` themselves to fix it permanently.
- The `shadcn@4.13.0` CLI installed via npx uses a new interactive-only "preset" init flow (Nova/Vega/Maia/...) with no non-interactive flag to skip it — components were hand-written instead of using `shadcn add`.

**Phase 3 — "Horario de Clases" — completed 2026-07-08 (same day).**
- Backend: `ClassScheduleController` (CRUD + `duplicateDay` + `currentClass` + `today`). Same-teacher time overlap on `store`/`update` returns 409 `requires_confirmation` (same pattern as grade-section deletes); same-classroom-different-teacher overlap never blocks, just returns a `warnings` array. `currentClass` compares `now()->isoWeekday()` + a plain `H:i:s` string comparison against `start_time`/`end_time` (avoids Carbon parse ambiguity — computed minutes-until-next-block via manual hour*60+minute arithmetic, not `diffInMinutes`, since that method's sign convention is easy to get backwards).
- Frontend: `/schedule` (desktop 6-column-by-day table, mobile day-tabs), `ScheduleBlockDialog.tsx`, and the dashboard's previously-static "Clase actual" card now polls `GET /schedule/current-class` every 60s and navigates to the grade sheet on click (not the full asistencia+calificar combined view from the spec — that's gated on the Asistencia phase, not built yet).
- **Real bug caught by testing, now fixed**: assumed Eloquent relation names serialize to JSON as camelCase (matching the PHP method name, e.g. `groupSubject`) — wrong. Laravel's `Model::relationsToArray()` snake_cases relation keys by default, so `ClassSchedule::groupSubject()` serializes as `"group_subject"` in JSON. Single-word relations used everywhere else in this project (`group`, `subject`, `teacher`, `institution`) never exposed this because snake_case and camelCase are identical for one word — `groupSubject` was the first multi-word relation consumed by the frontend, and it silently rendered blank labels until caught via a live curl of the endpoint. **Lesson: always verify actual JSON shape (curl or a passing E2E screenshot) before trusting an assumed relation-key casing in a new TS type — don't just pattern-match off memory.**
- Verified end-to-end with Playwright: created a real `class_schedules` row for the exact current server day/time via tinker, confirmed the dashboard card showed "🟢 Clase en curso" with correct salón/hora and navigated to the right grade sheet on click; desktop weekly grid and mobile day-tabs both render the seeded blocks correctly; added a new block through the dialog and saw it appear with a success toast. Zero console errors.

**Phase 4 — "Asistencia" — completed 2026-07-09.**
- Backend: `AttendanceController` (day view, range/history, `bulk`, `update`, `stats` ranking). `bulk` deliberately does NOT use `updateOrCreate()` — see the real bug below. History simplified to a filterable table (no visual month-calendar heatmap from the spec).
- Frontend: `/attendance` (tap-cycle button per student: `sin_registrar → presente → ausente_injustificado → tarde → ausente_justificado`, pre-loads existing records for the selected date, optional justification field for absences, "Marcar todos presentes"), `/attendance/history` (date-range table + expandable per-day detail + ranking de faltas). Dashboard's "Clase actual" card (Phase 3) now shows "📋 Asistencia: sin registrar" vs "✅ Asistencia registrada" for today, and its click target switches to `/attendance` when not yet registered (still deferring the full combined asistencia+calificar single screen from the spec).
- **Two real bugs caught by testing, now fixed:**
  1. Eloquent's `date`-cast attributes are persisted with a `00:00:00` time suffix (`fromDateTime()` always uses the full datetime format for storage, regardless of whether the cast is `'date'` or `'datetime'`) — but this is invisible against a real MySQL `DATE` column, which silently truncates it back to a pure date on insert. SQLite (used by the test suite) has no such column-type coercion and stores the literal string, so a plain `where('date', $rawString)` comparison against a raw HTTP query-string date silently returned zero rows in tests while looking fine against the dev MySQL DB. Fixed by switching to `whereDate(...)` for every exact-day comparison against a raw string in `AttendanceController`.
  2. The same storage quirk means `AttendanceRecord::updateOrCreate(['date' => $rawString, ...], ...)`'s match query would never find an existing row (exact string compare against a value stored with the time suffix) — so re-saving the same day's attendance would attempt a duplicate `INSERT` and violate the `(student_id, group_subject_id, date)` unique constraint instead of updating. This one **would have broken in production MySQL too**, not just in tests — re-passing lista for a day already registered would have thrown a 500. Fixed by resolving the existing record via an explicit `whereDate()` lookup first, then `update()` or `create()` manually instead of relying on `updateOrCreate()`. **Lesson: never use `updateOrCreate()`/exact `where()` equality against a plain date-only string on a Laravel `date`-cast column — always go through `whereDate()`, even when the match seems to work against MySQL in casual testing.**
- Verified end-to-end with Playwright: marked one demo student "ausente injustificado" with a justification via the tap-cycle UI, saved, then opened the grade sheet for the same period and watched "Asist" drop from 10.0 to 9.5 and the Aptitud "Def" follow it — with zero manual recalculation, confirming the Phase 2 (`GradeCalculatorService`)/Phase 4 (`AttendanceObserver`) integration end-to-end. Reloading `/attendance` for the same date correctly pre-loaded the saved statuses and justification text. History page and ranking de faltas rendered correctly. Zero console errors. Note: had to explicitly pick a date inside the seeded "Período 1" range (2026-01-20 to 2026-03-20) for the grade-recalculation check — the real "today" during this session (2026-07-10) falls in the demo's Período 3, which has no grade template applied, so attendance recorded against today's date has no `from_attendance` column to update.
- Mid-phase, MySQL was briefly down (`Connection refused` on 127.0.0.1:3306) and the Playwright scratch npm install also got wiped — both were transient environment resets, not code issues; user restarted MySQL and both were trivially recovered (backend tests are unaffected either way since they run on SQLite).

**Phase 5 — "Comportamiento y Anotaciones + Citaciones a Padres" — completed 2026-07-09.**
- Backend: `Student::isTaughtBy(User $user)`/`canBeAccessedBy(User $user)` (new reusable visibility rule — a teacher can see/manage a student's behavior annotations and citations if they're institution admin, registered the entry themselves, or currently teach any active group_subject for a group the student is actively enrolled in — matches the spec's "visible to every teacher who teaches this student," not just whoever wrote it). `BehaviorAnnotationController`, `ParentCitationController` (citation `updateStatus` requires `outcome` when status becomes `realizado`, via `required_if`), and a deliberately minimal `ParentController` (index/store/update for acudientes — just enough for the citation flow, not the full Perfil-del-Estudiante Acudientes tab).
- Frontend: `/behavior` (filtered list, "Nueva anotación" dialog scoped to the active course's roster, "¿requiere contactar?" toggle that auto-opens a pre-linked citation dialog on save) and `/citations` (filtered list with the spec's 6-state badge semaphore, inline "+ Agregar acudiente" during citation creation, "Marcar realizado" mini-form requiring outcome+commitments).
- **Another real bug caught by testing, same root cause as Phase 3's `groupSubject` one**: `BehaviorAnnotation`/`ParentCitation` both have a plain `registered_by` FK column *and* a `registeredBy()` relation — eager-loading that relation for display (`->with('registeredBy:id,name')`) silently overwrites the integer FK with the loaded User object at the same `registered_by` JSON key when the relation's snake-cased name collides with an existing attribute name, because `relationsToArray()` merges after `attributesToArray()` and the later write wins. Caught via direct curl comparison between `store` (no eager-load, `registered_by` = int) and `index` (eager-loaded, `registered_by` = object) responses for the *same* field. Fixed with a `withTeacherName()` helper in both controllers: load the relation, capture the name, `unsetRelation('registeredBy')`, *then* serialize — so the raw FK survives and the display name ships separately as `teacher_name`. **Lesson (generalizes Phase 3's): before eager-loading any relation for API output, check whether its snake_cased name collides with a plain column on the same model — if the model has both `x_id` and an `x()` relation whose camelCase name also snake-cases to something colliding with an existing key, loading it will silently clobber that key.**
- Verified end-to-end with Playwright: created a "negativa" annotation with "requiere contactar" checked → citation dialog auto-opened pre-linked to the same student → added a new acudiente inline → saved the citation → marked it "realizado" with outcome/commitments → confirmed the badge, student+parent name, and "Registrado por Hernis Mercado" all rendered correctly on both `/behavior` and `/citations`, desktop and mobile. Zero console errors.

**Phase 7 — "Tareas" (Homework) — completed 2026-07-10.**
- Unlike every prior phase, the `homeworks`/`homework_deliveries` migrations and Eloquent models (`Homework`, `HomeworkDelivery`) already existed from earlier scaffolding — this phase only added the controller, routes, and frontend.
- **Real bug caught immediately by the first test run**: the `Homework` model had no explicit `$table`, and Eloquent's pluralizer treats "Homework" as uncountable (same root cause as the Phase 1 `homework_deliveries` FK-guessing bug, documented back then) — it guessed table name `homework` (singular) instead of `homeworks`, causing `SQLSTATE... no such table: homework` on the very first insert. Fixed with `protected $table = 'homeworks';` on the model. **Lesson (generalizes the Phase 1 note): "homework" is uncountable in Laravel's pluralizer — always set `$table` explicitly on any model backed by a table literally named `homeworks`, not just its FK references elsewhere.**
- Backend: `HomeworkController` (index/store/update/destroy/deliveries/bulkDeliveries). The novel piece: a homework can "generate a grade column" (`is_graded` + `grade_section_id` + `weight` at creation) — `store()` creates a real `manual`-type `GradeColumn` in the chosen section (same pattern as `GradeColumnController::store`) and stores its id on `homeworks.grade_column_id`; `bulkDeliveries()` writes matching `Grade` rows via plain `Grade::updateOrCreate()` (not `withoutEvents()`) so `GradeObserver` fires and the normal section/period recalculation cascade runs — zero new grading logic needed. Authorization reuses the existing `GroupSubjectPolicy` (`$this->authorize('view'|'update', $homework->groupSubject)`) — no new Policy class, matching `GradeColumnController`'s approach.
- Frontend: `/homeworks` (list scoped to active course + active period via `useActiveCourseGroup()`/`useActivePeriod()`, client-side 🟢/🟡/🔴 due-date semáforo, "Nueva tarea" dialog with a conditional grade-section/weight picker when "¿Genera calificación?" is toggled) and `/homeworks/:homeworkId` (`HomeworkDeliveries.tsx`, roster with a tap-cycle status button — deliberately reusing `Attendance.tsx`'s pattern instead of building a new swipe-card mode — plus an optional score input per student when the homework `is_graded`).
- Verified end-to-end with Playwright: created a graded homework (section "Aptitud", weight 20%), registered one student's delivery as "Entregado" with a 9.0 score, confirmed the grade sheet (`/grades/:groupSubjectId/:periodId`) immediately showed the new "Taller de fracciones" column and a recalculated section "Def" (9.7) with zero manual recalculation step — full integration with the Phase 2 grading engine confirmed live, not just in the backend test. Also confirmed a teacher who doesn't teach the course gets a 403 on `/homeworks/{id}/deliveries` (checked via a direct authenticated `fetch()` call from a second logged-in browser page, reusing the `segundo.docente@uparaula.com` account created in Phase 6). Desktop and mobile screenshots both clean, zero console errors (aside from the intentionally-triggered 403 from the authorization probe itself).
- Backend test note: `after_or_equal:assigned_date` validation on `due_date` means test/demo data must pick due dates relative to the **real system clock** (assigned_date defaults to "today" client-side), not relative to the seeded academic period's date range — tripped up the first Playwright run attempt (picked a due date inside Período 1's 2026 range, which was earlier than the real current date and failed validation client-side as a silent 422). Not a product bug, a test-data mistake.

Files stored via the `local` disk (already pointed at `storage/app/private`, matching the spec's exact path convention) under `voice-notes/{institution_id}/{user_id}/{year}/`.
- **Real validation bug caught by the first test run**: used the `mimes:webm,mp3,ogg,wav` rule for the audio upload, which content-sniffs the file's magic bytes — Laravel's `UploadedFile::fake()->create()` test helper produces garbage content that fails content-sniffing regardless of the declared MIME type, so every test failed with `validation.mimes` (which cascaded into confusing 405/422 errors in unrelated assertions, since the dependent `$response->json('data.id')` came back null). Fixed by switching to `mimetypes:audio/webm,video/webm,audio/mpeg,audio/ogg,audio/wav,audio/x-wav` (header-based, not content-based) — the correct rule choice for any upload validated in tests via fake files, and still correct for real browser-recorded blobs. **Lesson: prefer `mimetypes` over `mimes` for any file-upload validation that will be exercised by `UploadedFile::fake()` in tests.**

Surfaced immediately as "Rendered more hooks than during the previous render" the moment a resize+reload changed the render path enough to matter. Fixed by moving the `useState` above the early return, alongside the component's other hooks. **Lesson: `tsc -b`/`npm run build` passing is not proof a page is safe — always exercise every page at least once with Playwright (including a resize/reload, which is what surfaced this one) before calling a phase done.**

Dashboard's `CurrentClassCard` gained a "📓 Clase anterior" chip (additive change, `stopPropagation`'d so it doesn't trigger the card's own click-through) opening `PreviousClassPlanDialog.tsx` with the "Usar como base para hoy" button, which navigates to `/plans?open={id}` — the list page reads that query param on mount and auto-opens the new entry.
- Verified end-to-end with Playwright, including real audio: launched Chromium with `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream` and `permissions: ['microphone']` on the browser context so `MediaRecorder` could record a real (synthetic) clip with no manual permission prompt — recorded a note under "pendiente", confirmed it appears as a playable "▷ 2s" chip and plays with zero errors. **Phase 9 — "Control de Copias / Fotocopias" — completed 2026-07-10.**
- Same pre-scaffolded pattern (`CopyCharge`/`StudentCopyPayment` models+migrations already existed). **Architecturally different from every phase since Phase 2**: copy charges key off `group_id` (a whole homeroom), not `group_subject_id` (one teacher's course) — `Group` has no "owning teacher" field, so authorization here is institution-wide (`$this->authorize('view', $group->institution)`, same gate `GroupController::students()` already used) rather than the "only who teaches this course" pattern used everywhere else. **Peso automático en tareas + escala de valoración institucional — 2026-09-26 (el usuario lo pidió dentro de la Fase 1).**
- **Norma consultada**: Decreto 1290 de 2009, art. 5 (compilado en el Decreto 1075 de 2015, art. 2.3.3.3.3.5): cada institución define su escala en el SIEE y debe expresar su equivalencia con la nacional (Superior, Alto, Básico, Bajo). Básico = superar los desempeños necesarios; Bajo = no superarlos. El SIEE lo aprueba el consejo directivo (art. 8). Preescolar se evalúa con informes descriptivos (Decreto 2247 de 1997, art. 14), no con esta escala. Rangos típicos en SIEE: 1.0–5.0 → Bajo 1.0–2.9, Básico 3.0–3.9, Alto 4.0–4.5, Superior 4.6–5.0; 1.0–10.0 → 1.0–5.9 / 6.0–7.9 / 8.0–9.4 / 9.5–10.0.
- **Backend**: tabla `performance_levels` (migración `2026_09_26_100000`, que siembra la escala sugerida para cada institución con su escala y nota mínima actuales). `PerformanceLevelController` (`GET`/`PUT /institutions/{id}/performance-levels`, `GET …/suggested`): se guarda completa y valida que empiece en 1.0, termine en el máximo, no tenga huecos ni cruces (pasos de 0.1), estén los cuatro niveles nacionales y la equivalencia no baje al subir la nota. Actualiza `grading_scale` y `min_passing_grade` (inicio del primer nivel que no es Bajo). `InstitutionController::update` ya no acepta esos dos campos (se desincronizarían); `store` siembra la escala. `InstitutionResource` incluye `performance_levels`. Reporte de planilla (xlsx/pdf) y boletín usan `PerformanceScale::tint($color)`; el boletín cambió la columna "Estado" (siempre "—", porque `is_promoted` nunca se calcula) por "Desempeño" + "Escala nacional", más una línea con la escala institucional.
- **Escala 1–5 de punta a punta**: las columnas nuevas (`bulk-save`) y las tareas toman `max_score` (y la nota base de asistencia) de la escala de la institución, no 10 fijo. Cambiar de escala no convierte notas ya registradas (la pantalla lo advierte).
- **Frontend**: `PerformanceScalePanel` (pestaña "Escala de valoración"): cada nivel edita solo su "hasta" (el "desde" se deriva, así no hay huecos), equivalencia nacional, color (paleta y "Otro"), muestra, vista previa en barra, validación en vivo y nota mínima resultante. Su borrador se recarga según el contenido guardado (JSON), no por la identidad del objeto: un refetch al volver a la ventana borraría lo que se está editando. `getGradeColor` usa el nivel de la escala (`setGradeScale` se llama en el render de `AppLayout`, no en un efecto, para que las páginas hijas ya la lean); `levelColors` usa `color-mix` con `--grade-level-text-mix` (negro en claro, blanco en oscuro). Leyenda "Escala:" sobre la planilla y el nombre del nivel como tooltip en cada nota.
- **Tareas**: `weight_mode: automatic` en `HomeworkController::store` reparte el 100 % de la sección por igual (un decimal, la última absorbe el redondeo), igual que "Automático" de Configurar planilla, y recalcula el curso. `store` también guarda `notes`, que antes ignoraba.
